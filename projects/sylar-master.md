# 项目：sylar-master

## 项目背景

- sylar-master 是一个开源的 C++ 网络框架：目标是在 Linux 上用“协程化 + 事件驱动”的方式组织高并发服务端程序，把网络 I/O、并发调度、协议栈与应用层框架能力做成可复用组件。
- 相比只提供 socket 封装的“网络库”，它更偏“服务框架”：除了 TCP/HTTP，还强调配置、日志、生命周期管理、可扩展的业务入口与模块边界，适合用来搭建网关、HTTP API、内部服务等。

## 技术介绍

- sylar-master 的关键价值在于把“高并发网络服务”的常见层次打通：
  - 底座：线程、锁、时间与定时器、日志、配置、工具类
  - 并发模型：协程（Fiber）+ 调度器（Scheduler）+ I/O 管理器（epoll 驱动）
  - 网络抽象：Address/Socket/Session/TcpServer 等，把“连接与读写”封装成可复用的会话模型
  - 协议与应用：在网络会话上实现协议解析与路由，把请求派发到业务逻辑（例如 HTTP 处理链）

## 核心机制（理解框架的关键）

### 1）协程化的非阻塞 I/O

- 目标是用“同步的写法”表达网络逻辑，但底层依然是非阻塞 socket：
  - 当业务协程执行到读/写但 fd 未就绪时，不阻塞线程，而是把当前协程挂起
  - I/O 管理器把 fd 注册到 epoll，等待可读/可写事件
  - 事件就绪后把协程恢复到可运行队列，继续执行后续逻辑
- 这样一来，线程数量可以更少，吞吐靠事件驱动与协程切换完成，而不是靠大量线程阻塞等待。

### 2）调度器：线程池承载协程

- 调度器的职责是“在一组工作线程上运行大量协程任务”：
  - 业务请求到来会被包装成任务（例如：处理一个连接、处理一个 HTTP 请求）
  - 调度器把任务分发到线程执行；当任务因 I/O 等待挂起时，线程继续执行其他协程
- 对业务开发者而言，关注点从“管理线程与锁”转移到“组织协程任务与状态机”。

### 3）I/O 管理器：epoll + 定时器一体化驱动

- I/O 管理器统一处理两类事件：
  - I/O 就绪：fd 的可读/可写/异常事件
  - 时间事件：超时、心跳、重试、周期任务
- 业务层常见需求（连接超时、请求超时、定时刷新缓存）可以统一通过“时间事件”实现，而不是散落在各线程 sleep 里。

## 业务逻辑层（从“写网络代码”到“写服务”）

这一层是开源网络框架最重要的落点：让你不需要每次都从 socket/线程开始，直接以“服务”的方式表达业务。

### 1）服务启动与装配（Bootstrapping）

- 典型流程可以理解为：
  1. 加载配置（端口、线程数、日志级别、路由规则、超时等）
  2. 初始化日志（输出目标、格式、滚动策略）
  3. 启动调度器/I/O 管理器（确定线程模型）
  4. 启动 Server（绑定地址、listen、开始 accept 循环）
  5. 注册路由/处理器（把请求映射到业务函数）
  6. 进入主循环（事件驱动 + 协程调度）
- 配置驱动的好处是：同一套二进制可通过配置切换环境（开发/测试/生产），并统一管理端口、线程、日志等运行参数。

### 2）连接与会话模型（Session）

- 框架通常会把“一个连接”包装为 Session：
  - Session 管理 socket 的生命周期：创建、读写、超时、关闭
  - 连接上的协议解析（例如 HTTP）通常发生在 Session 读到数据之后
- 业务层通常不直接操作 fd，而是对 Session 暴露的“收包/发包”接口进行交互。

### 3）协议解析与路由分发（以 HTTP 为例）

- HTTP 业务的关键不是 socket，而是“请求对象 → 路由 → 处理 → 响应对象”：
  - 解析：把字节流解析成 Request（method、path、headers、body）
  - 路由：按 path/method 命中 Handler（类似 Controller/Servlet）
  - 处理：执行业务逻辑，访问数据库/缓存/下游服务
  - 响应：构造 Response（status、headers、body），写回连接
- 业务开发时最希望拥有的能力包括：
  - 路由表/前缀匹配/参数提取（把 URL 映射到业务函数）
  - 统一异常处理（把错误转成标准响应）
  - 中间件式的前后置逻辑（鉴权、日志、限流、跨域、压缩）
  - Keep-Alive 与连接复用策略（减少握手开销）

### 4）中间件/拦截器思路（业务工程化）

- 开源网络框架的“业务层价值”往往通过一条处理链体现：
  - 请求入口：生成 traceId、记录访问日志
  - 安全与治理：鉴权、黑白名单、限流/熔断（可选）
  - 业务处理：调用 Controller/Service
  - 响应出口：统一封装响应、统计耗时、记录错误
- 这种组织方式能让横切逻辑不侵入业务代码，业务代码更聚焦于领域逻辑。

## 典型请求处理链路（可用来对照源码）

以“HTTP 请求 → 返回 JSON”为例，常见链路是：

1. Server accept 新连接，创建 Session
2. Session 在协程中循环读取数据，解析出完整 Request
3. Router/Servlet 根据 method + path 选中对应 Handler
4. Handler 执行：参数校验 → 调用业务 Service → 构造 Response
5. Session 写回 Response，按 Keep-Alive 决定是否复用连接
6. 超时/错误触发统一处理：返回错误码并关闭连接或继续等待

## 适用场景

- HTTP API 服务：提供 REST 风格接口，配合路由与中间件组织业务
- 内部网关/代理：在业务层做鉴权、路由、转发、灰度策略（需要自行扩展上游/下游逻辑）
- 长连接服务：连接管理、心跳、超时、重连等，借助定时器与 I/O 事件组织状态机
